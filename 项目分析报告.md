● Chatwoot v4.15.1 深度分析报告

  经过对仓库做全方位的源码研究（54 个 model、12 种 channel、4 个 Vue 入口、~80 个 background job、~60 个 API controller），以下是"看完等于在源码里走了一遍"的透彻理解。

  ---
  一、Chatwoot 到底是什么

  一句话定义：Chatwoot 是一个多租户 omnichannel
  客服平台，让一个企业把所有渠道（网站、邮件、WhatsApp、Instagram、Facebook、Telegram、Line、TikTok、Twitter、SMS、Twilio、API）的客户对话拉进一个统一收件箱，配以协作工作流、AI 辅助、Help
  Center、报表分析，且支持自托管——是 Intercom / Zendesk / Salesforce Service Cloud 的开源替代品。

  与 Intercom/Zendesk 不同的核心定位：
  - 自托管优先：MIT 协议，任何人能跑在自己的服务器上。Docker 一键启动。
  - 白标可定制：useBranding composable 把"Chatwoot"全部替换为客户品牌名。
  - 对话是核心（不是 ticket）：UI/UX 默认就是聊天界面，不是工单编号。
  - AI 是第一公民：Captain 模块从 V1 就内置了 LLM 能力，不靠外部 AI 服务。

  项目量级：
  - Ruby 3.4.4 + Rails 7.1 后端
  - Vue 3 + Vite + Pinia/Vuex 前端
  - PostgreSQL + pgvector（向量检索）
  - Sidekiq + Redis（异步 + 缓存 + ActionCable）
  - 约 54 个核心 AR model、12 个 channel 类型、~60 个 Vuex module、~80 个 Sidekiq job

  二、整体架构全景

  2.1 4 个独立的前端入口

  Chatwoot 把不同受众的 UI 拆成完全独立的 Vue 3 应用，编译成不同 bundle（dashboard.js / widget.js / sdk.js / portal.js），通过 Vite 多 entrypoint 模式实现。

  为什么要拆四个？因为它们安全上下文完全不同：
  - Widget 在第三方域名的 iframe 里运行（300 KB 体积限制），
  - Dashboard 在 Chatwoot 自己的 origin 用完整 session（好几 MB，能装 Twilio SDK），
  - SDK 是浏览器端 vanilla JS（40 KB 限制），
  - Portal 是 SEO 关键的 SSR（必须 server-rendered HTML）。

  共享代码在 app/javascript/shared/（composables、API helper、ActionCable 基础类、i18n 配置）。

  3.2 12 个核心设计决策（"为什么"系列）

  (1) 为什么 ContactInbox 独立成一张表？

  一个客户能从多个渠道（邮件 + WhatsApp + 网站）找你；一个 inbox 也可能对应多个客户（罕见但合法，比如共享邮箱）。如果用 Inbox.contact_id 直接外键，就没法表达"同一个 contact 在多个
  inbox"。ContactInbox.source_id 存的是渠道特定的不透明 ID（WhatsApp 是手机号、Email 是邮箱、WebWidget 是 UUID），pubsub_token 是 ActionCable 认证的"每人每会话一票据"。

  (2) 为什么 Channel 用多表而不是 STI？

  12 种 channel 字段集差异极大——Channel::Email 要 SMTP/IMAP 凭据，Channel::Whatsapp 要 provider_config JSONB，Channel::FacebookPage 要加密的 page_access_token。STI 会强制一张稀疏大表；不同
  channel 的加密列、生命周期 hook（Channel::Telegram 创建时调 setWebhook）、唯一性约束都不同。多表 + 多态 = 灵活 + 清晰。

  (3) 为什么 Message 的 sender 是多态？

  一个会话里 sender 可能是 User（agent）、Contact（客户）、AgentBot（外部 bot）、Captain::Assistant（AI 助手）。多态用一个 sender_type + sender_id 就覆盖所有情况，不用为每种 sender 类型拆表。

  (4) 为什么 Conversation 的 display_id 用每租户 DB 序列？

  URL 形如 /conversations/42 —— 短、人类可读。如果用全局自增，租户 A 能推断"租户 B 业务规模"；如果用全局 UUID，又太长不友好。每个 Account 创建时触发一个 Postgres conv_dpid_seq_<id>
  序列，给每租户一个独立的"自动编号"。app/models/account.rb 第 187-193 行就是触发器。

  (5) 为什么 API 限流有专门的"防举报攻击"throttle？

  Widget 是公开 API，恶意访客能灌爆你的收件箱。api/v1/widget/conversations 的 throttle 是 6 per 12 hours per IP —— 极端严格，这是产品决策：客服系统最怕的是会话被恶意客户灌爆。

  (6) 为什么 reply+UUID@domain 是邮件路由的核心魔法？

  outbound 邮件的 Reply-To 设成 reply+<conversation-uuid>@<inbound-email-domain>，客户回复时无论用什么邮件服务（Gmail/Outlook/SES/Postmark）都自动路由回原会话。这让 Chatwoot 不需要写 5 个
  provider 的 inbound webhook（Mailgun/Mandrill/Postmark/Sendgrid/SES），一个 ActionMailbox 路由规则吃下所有。这是个用"邮件协议"做路由的优雅例子。

  (7) 为什么 Bot 访问令牌有白名单而不是 RBAC？

  BOT_ACCESSIBLE_ENDPOINTS 是一张硬编码的 controller_path => [actions] 哈希表（4 个 controller，每个 1-7 个 action）。因为 bot 的需求简单——"bot
  像人一样参与会话"——只需要会话/消息/标签/分配四个端点。白名单比 RBAC 简单且更难写错。access_token_auth_helper.rb 第 N 行就是这张表。

  (8) 为什么 Pub/Sub 用 Wisper + 自研 Dispatcher 而不是直接用 ActiveSupport::Notifications？

  Wisper 提供 publisher.subscribe(listener) 的显式订阅语义；app/dispatchers/dispatcher.rb 把它包装成 Singleton，提供 sync + async 双路径：sync 立即广播（用于 ActionCable 实时推 + AgentBot
  webhook），async 入 EventDispatcherJob (queue :critical)。这意味着即使 Sidekiq 卡了，前端实时 UI 也不会卡。

  (9) 为什么锁用 Redis 而不用 PostgreSQL advisory lock？

  Webhook 并发处理（同一个 wamid 被 Meta 推两次）是高频场景；Sidekiq 跑在多进程多机器上，Postgres advisory lock 需要每个 worker 都连 PG；Redis lock（SET
  NX）更轻量、跨进程原子。MutexApplicationJob + with_lock 是通用模式。

  (10) 为什么 Account 的 settings 是 JSONB 而不是新建列？

  Chatwoot 已经支持 20+ 个账户级配置（locale、auto_resolve_after、captain_models、captain_features...）。每加一个都要 ALTER TABLE + 迁移，迭代慢。JSONB + JSON Schema 验证 =
  新增配置零迁移。但只对"无关系、不需要查询的叶子设置"用 JSONB；display_id、status 这类强查询字段仍是独立列。

  (11) 为什么 Canned Response 没有自动化 trigger？

  和 Macro/AutomationRule 是三个完全不同的概念：
  - Canned Response：纯文本片段，agent 在 composer 里按 / 触发插入，没有任何动作。
  - Macro：agent 手动对单个会话执行的多步骤动作包（assign + label + send_message），有 visibility: personal/global。
  - AutomationRule：事件驱动的 if-this-then-that（"new conversation + has label 'billing' → assign to team X"），永远在后台跑。

  三个抽象的 trigger 维度是"人工手动 / 事件触发 / 文本片段插入"——不同的 UX 时刻。

  (12) 为什么 Helper (bot 集成) 用两个模型（Hook + App）？

  - Integrations::App 不是 AR model，是 config/integration/apps.yml 的内存包装。每个 App 描述"这是什么集成"（OAuth URL、支持的字段、多实例是否允许）。
  - Integrations::Hook 是 AR model，每行代表"某个账户装了某个 App 的某个实例"。

  一个 Slack App → 多个 Slack Hook 是不允许的（allow_multiple_hooks: false），但 Dialogflow 一个账户可以装多个（每个 inbox 独立）。App = 模板；Hook = 安装实例。这是经典的"产品 vs 安装"分离。

  4.2 入站消息的统一处理流程

  所有 channel 走同一个 5 步链路：

  [Channel Webhook] → [Controller 验签 + 200 OK] → [Sidekiq Job 加锁]
    → [Incoming*Service 归一化 payload] → [MessageBuilder 写 DB]
      → [after_create_commit 触发 SendReplyJob + Dispatcher]

  为什么 webhook controller 只验签就 200？ 防止 provider 重试风暴；让 Sidekiq 异步处理重活。为什么 webhook job 要加 Redis 锁？ 防止同一个 wamid 被 Meta 推多次时双扣费。为什么还要 source_id
  短路？ 第三道防线——find_message_by_source_id 在写之前再查一次。

  双层 lib/integrations/ vs app/builders/messages/：lib/integrations/facebook/* 负责解析原始 JSON（preprocessing），app/builders/messages/facebook/message_builder.rb 负责写数据库（写）。Slack
  不一样——它的"会话"在 Slack 自己那边，所以 lib/integrations/slack/incoming_message_builder.rb 是个桥接器，不写 Chatwoot DB。

  4.3 出站消息的统一分派

  SendReplyJob 维护一张静态 CHANNEL_SERVICES 映射表：

  'Channel::TwitterProfile' => Twitter::SendOnTwitterService,
  'Channel::TwilioSms' => Twilio::SendOnTwilioService,
  'Channel::Line' => Line::SendOnLineService,
  'Channel::Telegram' => Telegram::SendOnTelegramService,
  'Channel::Whatsapp' => Whatsapp::SendOnWhatsappService,
  'Channel::Sms' => Sms::SendOnSmsService,
  'Channel::Instagram' => Instagram::SendOnInstagramService,
  'Channel::Tiktok' => Tiktok::SendOnTiktokService,
  'Channel::Email' => Email::SendOnEmailService,
  'Channel::FacebookPage' => Facebook::SendOnFacebookService,  # IG DMs 特例：additional_attributes['type'] == 'instagram_direct_message' 走 Messenger 路径
  'Channel::WebWidget' / 'Channel::Api' => Messages::SendEmailNotificationService  # 仅通知 agent 邮件

  新增 channel 只需要两步：（1）加一个 Channel::Xxx model；（2）加一个 SendOnXxxService + 在 CHANNEL_SERVICES 登记一行。所有 channel 共享 Base::SendOnChannelService
  的防自发自循环检查（outgoing_message_originated_from_channel? 看 source_id）。

  4.4 消息模型的关键设计

  4 种 message_type：incoming / outgoing / activity（系统活动消息，如"已分配给 X"）/ template（WhatsApp 模板消息）。

  13 种 content_type（按用途分）：
  - text (0) — 默认文本
  - input_text/input_textarea/input_email/input_select (1-4) — bot 向用户收集输入
  - cards/form (5-6) — 富卡片/表单
  - article (7) — Help Center 文章链接
  - incoming_email (8) — 邮件入站
  - input_csat (9) — 满意度调查按钮
  - integrations (10) — 集成生成（如 Linear 自动链接）
  - sticker (11) — LINE 表情包
  - voice_call (12) — 语音通话状态

  content_attributes JSON store 存 16+ 个标准键：in_reply_to、external_error、translations（Google Translate
  翻译缓存）、transcribed_text（语音转写）、email.html_content/text_content（邮件双格式）、automation_rule_id（标记自动化发出的消息，避免计入"首响"）等。

  关键回调（Message#after_create_commit）：
  1. reopen_conversation（snoozed/resolved 自动重开，bot 拥有的会话改 pending）
  2. set_conversation_activity（更新 last_activity_at）
  3. dispatch_create_events（发 MESSAGE_CREATED 事件 + 若是首条有效人工回复发 FIRST_REPLY_CREATED）
  4. send_reply（仅 outgoing：SendReplyJob.perform_later，附件时等 2s 让 ActiveStorage 上传完）

  ---
  五、对话与会话的生命周期

  5.1 4 个状态

  Conversation.status enum：open (0) / resolved (1) / pending (2) / snoozed (3)

  转换规则：
  - incoming 消息到 snoozed → 自动 reopen 到 open
  - incoming 消息到 resolved → API channel/人工 inbox 直接 reopen 到 open，bot 拥有的 inbox 改 pending（让 bot 接管）
  - blocked contact → before_create 钩子直接设为 resolved
  - 启用 bot 的 inbox → 新会话默认 pending
  - 客户标 "blocked" → 自动 resolved

  5.2 分配

  双字段：assignee_id (User) + assignee_agent_bot_id (AgentBot)，不是 polymorphic——保留 integer FK 走热路径索引。这是显式的设计权衡：conversation.rb 第 196 行注释说"Virtual attribute till we
  switch completely to polymorphic assignee"。

  两套自动分配（feature flag assignment_v2 切换）：
  - V1（legacy）：AutoAssignment::AgentAssignmentService + Redis round-robin 队列
  - V2：AutoAssignment::AssignmentService + RateLimiter（5 分钟内最多 100 个分发）+ AssignmentPolicy 模型 + InboxAssignmentPolicy 关联 + FOR UPDATE SKIP LOCKED 防并发双分配

  5.3 过滤 DSL

  lib/filters/filter_keys.yml 是所有可过滤字段的中央目录——labelable_conversation_filter / attribute_changed / is_present / days_before 等 13+ 种 operator。FilterService 把它编译成 Arel SQL
  片段。这是用 YAML 描述 DSL、用 service 编译的经典做法——新增一个可过滤字段只需要在 yml 加一行。

  7.1 多租户三层隔离

  1. URL 强制：/api/v1/accounts/:account_id/... 把租户 ID 放进 URL；Api::V1::Accounts::BaseController#current_account before_action 拦截。
  2. 行级隔离：Pundit 政策，每个 resource 都有 *_policy.rb + Scope 类限定可访问的行。
  3. Thread-local context：lib/current.rb 提供 Current.user/Current.account/Current.account_user/Current.executed_by——services 不需要显式传账户 ID，模型回调里也能读。

  7.2 Pundit 的 user_context 模式

  class ApplicationPolicy
    def initialize(user_context, record)
      @user = user_context[:user]
      @account = user_context[:account]
      @account_user = user_context[:account_user]
    end
  end

  user_context 是 { user, account, account_user } 哈希——因为 99% 的检查都需要全局 user + 该租户的角色两个上下文。打包成一个 hash 让 policy 签名统一。

  7.3 22 个 Rack::Attack 限流规则

  config/initializers/rack_attack.rb 是产品决策的硬编码：
  - 登录：5/5min by IP, 10/15min by email
  - 重置密码：5/30min by IP, 5/1h by email
  - MFA 验证：5/1min by IP, 10/1min by token
  - Widget 防轰炸：POST /api/v1/widget/conversations 6/12h（最严格）
  - API 报告：/api/v2/accounts/:id/reports 100/min by user, 1000/min by account

  每个被阻止的请求都会被记录（带 mask 后的 token/IP）用于安全审计。

  7.4 SafeFetch SSRF 防护

  lib/safe_fetch/fetcher.rb 是 Chatwoot 自己写的 URL 抓取器（不直接用 Net::HTTP）——因为 Chatwoot 要去抓客户网站（Captain 爬文档），必须防 SSRF：
  - 默认走 ssrf_filter gem，阻止所有内网 IP（防止 169.254.169.254 这类云元数据）
  - 自定义 PrivateNetworkRequest：当 SAFE_FETCH_ALLOW_PRIVATE_NETWORK=true 时允许内网，手动解析域名、随机选 IP、跟随时 strip Authorization/Cookie 头（防 redirect 到外网泄露）
  - 流式下载到 Tempfile（不加载到内存），限制 MAXIMUM_FILE_UPLOAD_SIZE（默认 GB 级）
  - 验证 Content-Type 只能是 image/*/video/* 或白名单

  十三、通知（Web Push + FCM + ChatwootHub）

  13.1 三层降级

  Notification::PushNotificationService#perform：

  1. Web Push（VAPID，webpush gem）—— 浏览器订阅走这个
  2. FCM v1（Google::Auth::ServiceAccountCredentials）—— 有 Firebase 项目时
  3. ChatwootHub relay（ENABLE_PUSH_RELAY_SERVER=true）—— 自托管 OSS 用户默认走这里——通过 Chatwoot 官方 relay 服务转发

  为什么自托管 OSS 需要 relay：自托管用户大多数没有自己的 Firebase 项目。ChatwootHub 让 OSS 安装也能用 push notification——这是个非常聪明的设计。

  13.2 Notification 模型

  Notification 表有两个多态 actor：primary_actor（Conversation）+ secondary_actor（Message）。UNIQUE 约束保证同一 (user, conversation) 一条新消息通知。

  after_create_commit 触发三类 job：
  - Notification::PushNotificationJob（if push enabled）
  - Notification::EmailNotificationJob（if email enabled）

  十四、关键 cross-cutting 模式总结

  14.1 6 个"跨切关注点"模式

  1. Pub/Sub everywhere：webhook、hook、notification、reporting、automation、ActionCable 全是 BaseListener Singleton。加新副作用 = 加 listener。
  2. Current thread-local：所有 model/service 能读 Current.user/Current.account/Current.account_user/Current.executed_by。Sidekiq 任务有独立 thread copy。
  3. JSONB + JSON Schema 校验：Account.settings / Inbox.csat_config / Webhook.subscriptions / AutomationRule.conditions/actions / Campaign.audience/trigger_rules /
  Captain::CustomTool.param_schema —— 新增配置零迁移。
  4. 每租户 Postgres 序列：conv_dpid_seq_<id> / camp_dpid_seq_<id> —— per-account 友好 URL（/conversations/42）+ 不泄露租户规模。
  5. prepend_mod_with / include_mod_with / extend_mod_with：OSS 文件保持干净；EE 文件在 enterprise/ 下通过祖先链 prepend 进来。AOP 风格扩展。
  6. CHANNEL_SERVICES 中央分派表：SendReplyJob 维护的 class => service 映射。加新 channel = 加 1 行 + 1 个 SendOn service。

  14.2 4 个"小但关键"的工程细节

  - has_secure_token 大量使用：Channel::WebWidget 的 website_token + hmac_token、Channel::Api 的 identifier + hmac_token、ContactInbox 的 pubsub_token —— 每个都是 URL-safe 32 字节随机串。
  - MutexApplicationJob：Sidekiq 任务的 Redis 互斥锁基类，所有 webhook job 都继承它。
  - prepend_mod_with('SearchService') 让 EE 覆盖搜索：OSS 用 GIN/ILIKE，EE 加 OpenSearch；fail 优雅降级。
  - Base::SendOnChannelService 防御性检查：validate_target_channel（防止 dispatcher 错配 channel）、outgoing_message?（只 outgoing/template）、invalid_message?（private/已 echo/voice_call
  都跳过）—— 一处拦截所有"无效出站"场景。

  十六、Chatwoot 的"商业本质"和"技术价值"

  16.1 商业本质

  Chatwoot 解决的是 B2B/B2C 企业的"客户支持碎片化"问题。8 个真实痛点：

  1. 渠道碎片化 → omnichannel 统一收件箱
  2. 协作黑洞 → conversation 状态 + 分配 + @提及 + 私有备注
  3. SLA 失控 → 首响时间/解决时间统计 + SLA 告警（EE）
  4. 重复问题淹没 → Canned Response + Macro + Help Center + Captain FAQ bot
  5. 客户数据散落 → 统一 Contact 模型跨渠道累积
  6. 主动触达困难 → Campaign（URL 触发 + 业务时间内）
  7. 运营盲点 → Reports / CSAT / Live View
  8. AI 浪潮 → Captain（LLM + RAG + Tool-use 内置，无外部 AI 服务锁定）

  16.2 技术价值（学 Chatwoot 你能学到什么）

  - Webhook 集成怎么做得优雅：controller 验签 + 立即 200 + 异步 job 加锁 + 写之前 source_id 短路——4 层防护
  - 多租户怎么做干净：URL 强制 + Pundit + Current thread-local
  - Pub/Sub 怎么做轻量：自研 Dispatcher Singleton + Wisper + sync/async 双路径
  - 多 channel 怎么避免 if-else 地狱：CHANNEL_SERVICES 中央分派表 + 共享 Base::SendOnChannelService 防御检查
  - AI 怎么分层：V1 单调用 → V2 multi-step agent + tools，feature flag 平滑切换
  - 企业版怎么做不发版分叉：prepend_mod_with AOP 风格
  - 怎么用 JSONB 避免 schema 频繁迁移：JSONB + JSON Schema 校验
  - 白标怎么不漏：单一 useBranding composable 全部替换品牌名

  16.3 为什么 Chatwoot 值得学习

  - 规模恰当：54 个 model、12 个 channel、~80 个 job——不臃肿也不过分简单。
  - 设计成熟：每个 model/concern 都有清晰单一职责；service/job/listener 分层明确。
  - 真实生产：每月百万级会话（自报），Docker Hub 上千万次拉取。
  - 完整文档化：CLAUDE.md 把所有开发流程、代码规范、Enterprise 注意事项都写清了。
  - 社区活跃：114 种后端语言 / 56 种前端语言，GitHub 17k+ stars。
  - AI 走在前面：Captain V2 完整 RAG + Agent runner 在 OSS 阶段就设计好了，比多数客服 SaaS 都早。

  总结

  Chatwoot 不是一个"半成品开源玩具"，而是一个有清晰产品定位、严谨工程实践、清晰商业化路径的成熟客服平台。它的核心是把"客户支持"这个 B2B SaaS
  垂直做透——不是聊天机器人，不是工单系统，是真正的"omnichannel customer support platform"。开源版覆盖核心能力，企业版覆盖 SLA/SSO/高级 AI/计费，是 Chatwoot 商业化的支柱。

  了解完这一切后，你应该能回答这些问题：
  - "为什么不用 STI 存 channel？" → 多表多态
  - "为什么 webhook 验签就 200？" → 防 provider 重试
  - "为什么 Sidekiq 限流在 widget 是 6/12h？" → 防客服系统被恶意灌爆
  - "为什么 EE 用 prepend_mod_with？" → 不发版分叉加功能
  - "为什么 Captain V1 和 V2 同时存在？" → 平滑迁移，不破坏现有客户
  - "为什么 reply+UUID 是邮件路由的魔法？" → 任何 provider 都能用
